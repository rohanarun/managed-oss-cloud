# Checkout capacity holds

Hosted checkout reserves physical worker capacity before a Stripe Checkout Session is created. The reservation is durable in PostgreSQL, assigns each planned application to a specific worker, expires after 60 minutes, and counts against worker placement while it is active. Stripe Checkout Sessions expire after approximately 35 minutes, leaving a safety window before the hold can be reused.

The paid webhook accepts the exact hold named in both Session and Subscription metadata even when signed delivery arrives after that hold expired. It verifies the Stripe customer, Session, Subscription, user, installation, plan, application snapshot, managed price components, and worker allocations. An active hold is consumed in one database transaction that fixes each application to its held worker, records the subscription and Stripe event, creates worker-bound install jobs, and marks the hold consumed. Replays do not create another subscription or job.

An expired hold is never revived or silently consumed. Under the same global capacity lock, the webhook revalidates the immutable application snapshot against the current healthy worker pool. If the applications fit, it atomically places them, creates the quota and jobs, and records a fulfilled recovery. If they do not fit, the transaction records the signed Stripe event, a non-entitled `paid_pending_capacity` subscription, and a durable recovery obligation. No allocation, route, application assignment, or install job is created in that pending state.

The separately deployed subscription reconciliation worker advances every obligation. Before the configured deadline it retries placement only from an exact active or trialing provider subscription whose owner, installation, customer, capacity-hold metadata, and two managed prices match the stored obligation. Temporary invalid or missing provider rows cannot turn `paid_pending_capacity` into an entitlement and cannot erase the recovery ledger. At the deadline the worker transitions the local subscription to `compensation_required` even when Stripe is temporarily missing from the listing.

Failed customer or Checkout Session creation releases the hold. A Session that was created but could not be attached locally is expired at Stripe before its hold is released; if expiration cannot be confirmed, the hold remains active and fails closed. Abandoned active holds stop counting after their expiry.

## Compensation contract

A worker can become unhealthy or go offline after checkout starts. The hold proves that physical capacity was available and prevents it from being allocated elsewhere, but it cannot guarantee future machine health. `PAID_CAPACITY_RECOVERY_WINDOW_MILLISECONDS` bounds how long a recognized payment may remain pending; the default is 24 hours.

`compensation_required` has one explicit action: `cancel_subscription_and_refund_captured_payment`. The apply-mode reconciliation worker retrieves the exact subscription, Checkout Session, initial paid invoice, and invoice payments; it fails closed on any owner, customer, hold, price, currency, invoice, or payment mismatch. It cancels the subscription without another invoice or proration and refunds only the proved captured-payment remainder. Stable Stripe idempotency keys prevent duplicate cancellations and refunds. Existing successful refunds count toward the exact remainder, pending refunds are observed rather than duplicated, and a failed managed refund requires operator review.

The repository itself never calls Stripe and never infers success from a cancellation request. The worker changes the local recovery to `compensated` only after Stripe reports the exact subscription canceled and every captured invoice payment fully refunded, storing the subscription, invoice, and refund IDs as the durable compensation reference. That final transaction also changes the local subscription to `canceled`. A terminal compensated attempt does not prevent the same planned installation from starting a later legitimate checkout; a partial uniqueness constraint permits only one pending or compensation-required obligation per installation.

Hosted billing must not be enabled without the `subscription-reconciler` Compose service running under the `billing` profile in `apply` mode and alerting on `paid_capacity_recovery_pending` and `paid_capacity_compensation_required`. Dry-run mode reports obligations but intentionally performs no placement retry, cancellation, refund, or state transition.
