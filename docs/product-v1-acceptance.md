# Product v1 acceptance and feature-completeness matrix

## Purpose

This document is the release contract for the 37 original first-party products defined by the Managed OSS Cloud registry. The current registry contains 407 typed actions. Each independent product distribution exposes its product action set through a scoped HTTP client, command-line interface, stdio MCP server, and browser surface while the shared control plane remains the only database and authorization owner.

The product names listed as references below identify broad software categories only. They do not establish source, UI, API, data-model, import-format, or behavioral compatibility with an incumbent. A product can complete this declared v1 contract without matching every feature of the referenced incumbent. Conversely, registering every action or rendering an action console does not prove that the product has completed v1.

The following terms are distinct:

- **Declared-action completeness** means every workflow action in this matrix exists in the source registry with a closed typed schema, stable action and MCP names, scope and risk metadata, and a product manifest entry.
- **Source implementation** means the action reaches its registered domain engine and its source-level invariant and integration tests pass.
- **Product v1 acceptance** means the source implementation also passes every shared and product-specific gate in this document with current runtime evidence.
- **Incumbent parity** is not claimed by this repository and must never be inferred from a category reference, action count, screenshot, or successful test.

## Shared product and persistence contract

These requirements apply to every product row.

1. **One authoritative API.** The HTTP API is the behavioral implementation. Browser, CLI, and MCP requests must use the same action definition, authorization, validation, transaction, and result path.
2. **No product-owned database.** Generated product repositories must not receive PostgreSQL credentials, own migrations, or create a parallel source of truth. They authenticate to the control plane with a scoped bearer token and call /api/suite/modules/{moduleId}/actions/{actionId}.
3. **Tenant isolation.** Every durable row carries workspace ownership. Authenticated context, never request JSON, selects the workspace. PostgreSQL row-level security is enabled and forced for runtime roles, and two-workspace tests must prove that records, evidence, shares, exports, AI requests, and receipts cannot cross the boundary.
4. **Durable business facts.** Business entities use immutable identifiers, explicit lifecycle states, creation and modification clocks, optimistic versions, portable versioned exports, retention/deletion classes, and append-only receipts for security-sensitive or externally visible mutations.
5. **Retry and approval safety.** Idempotency keys bind the workspace, module, action, and canonical request. Hash/version checks, dry runs, attributed approvals, database uniqueness constraints, and exact effect receipts remain in force where the action contract requires them.
6. **External effects remain explicit.** A dispatch plan, checkout command, publication request, provider identifier, or elapsed time is not evidence that an external effect occurred. Provider execution belongs to a reviewed adapter, and accepted, delivered, paid, published, checked in, or revoked states require the exact evidence defined by the module.
7. **AI remains proposal-bound.** AI actions receive only selected tenant-owned evidence, record the actual model and prompt contract, return cited review-pending results, and cannot silently publish, send, charge, hire, alter access, or mutate another workflow.
8. **Secrets remain outside records and model context.** Provider credentials, bearer tokens, private signing material, unrestricted paths, arbitrary SQL, and shell commands are not accepted by product action or MCP contracts.

## Shared CLI, MCP, and browser acceptance

Every product CLI must expose version, manifest, actions, action-help, workspace, enable, list, ai-status, and action execution. Every product MCP server must expose four product utilities—workspace, enable, list_records, and ai_status—plus one separately named typed tool for every declared action. Thus a product with N actions has N + 4 MCP tools.

CLI and MCP acceptance requires:

- closed schemas and unknown-field rejection before the network request;
- correct read, write, and AI token-scope enforcement;
- action-by-action permission tests, including destructive and consequential operations;
- the same durable identifiers, records, receipts, and replay result as HTTP;
- no generic record-mutation, generic AI, arbitrary SQL, shell, or provider-secret escape hatch; and
- live parity tests, not manifest enumeration alone.

The shared generated JSON action console is a diagnostic surface. It may prove that an action can be selected and submitted, but it does not by itself satisfy the browser workflow gate. Each product needs a usable domain-specific flow for its primary outcome, with understandable validation, loading, error, confirmation, empty, and completed states. Screenshots of a generic console are not feature-completeness evidence.

## Shared completion gate

A product is accepted as v1 only when all behavioral tests in its linked clean-room specification pass at the described public interface and scope, plus:

1. isolation tests with two real workspaces;
2. permission tests for every CLI and MCP mutation;
3. restart and backup/restore durability evidence;
4. export and deletion evidence;
5. dependency, license, provenance, secret, and copied-string audits;
6. a live browser workflow for the primary user outcome, including the accessibility requirements in the product specification;
7. CLI and MCP parity against the same durable records; and
8. current adapter, public-route, signing, storage, or provider evidence required by the product-specific boundary below.

Build success, a health endpoint, registry enumeration, a mocked API, a manifest screenshot, or a provider-queued response cannot substitute for these gates.

## Source of truth

- Product and plan registry: src/shared/suite.ts
- Typed action aggregation and legacy specialist actions: src/shared/suite-actions.ts
- Family action registries: src/shared/core-business-actions.ts, src/shared/first-party-growth-actions.ts, src/shared/additive-business-actions.ts, src/shared/extended-business-actions.ts, src/shared/premium-business-actions.ts, src/shared/esign-actions.ts, and src/shared/email-actions.ts
- Independent repository mapping and generated CLI/MCP/browser contract: scripts/generate-product-repositories.mjs
- Shared clean-room and completion gate: docs/clean-room/README.md
- Module specifications: the linked family and product records under docs/clean-room/

If the registry, action count, product manifest, or a module specification changes, this matrix must be reviewed in the same change. A generated repository release may advertise v1 acceptance only after its exact backend release and every applicable gate above have current, reproducible evidence.
